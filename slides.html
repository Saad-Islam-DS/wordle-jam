What we built

A fully playable Wordle clone — in a browser, no install.

Core

  • Six 5-letter guesses
  • Green / yellow / absent scoring
  • On-screen and physical keyboard
  • 15,921-word dictionary
  • Non-repeating random answers

Polish

  • Tile flip animation on reveal
  • Absent keys hide from keyboard
  • Shake on invalid guess
  • Win / lose modal + play again
  • Mobile layout + color legend

Our approach

"Humans own ideas, architecture, and merge decisions. Claude drafts code; humans review every line before it lands."

Humans in the loop

  • Each person opens Claude Code in their own machine
  • Claude reads shared context from the repo, not from us
  • No teammate waits on a middleman

Claude as a tool

  • Drafts code from atomic tickets
  • Never pushes directly
  • Humans approve every PR

Deciding the stack & the split

Why plain HTML/CSS/JS

  • Zero install for 3 people
  • No bundler = no 20-min setup tax
  • Wordle is DOM-shaped — green/yellow tiles are divs
  • Clean 3-file split = clean 3-person split

Not Godot: 30-min install + .tscn merge conflicts would have eaten the budget.

File-boundary ownership

  • A → src/game.js (logic)
  • B → src/ui.js + styles.css
  • C → src/input.js + assets/words.txt

Strict boundaries = zero merge conflicts across 16 PRs.

Standing on Benjamin's shoulders

Sudoblark — "LLMs in the SDLC"

The six phases

  • Plan — AI drafts tickets; humans prioritize
  • Design — AI lists trade-offs; humans decide
  • Implement — AI codes; humans review every diff
  • Test — AI writes tests; humans verify fitness
  • Deploy / Maintain — humans always drive

What we adopted

  • Atomic tickets as files in work/
  • One ticket = one branch = one PR
  • Tiny commits, mandatory teammate review
  • CLAUDE.md + ARCHITECTURE.md as the shared brain
  • Per-person onboarding docs (PERSON_A/B/C.md)

The workflow — per ticket

Never a direct commit to main. Never a self-merge of code (only chore commits).

Honest moments

Where the "human" in the loop earned its name

  • The scoring-test trap. Claude wrote assertions with the expected values wrong. Human caught them failing in the browser console — we fixed the test, not the code.
  • The missing Z key. Scaffold used 'Zxcvbnm B' as a shorthand — no actual Z on the keyboard. Person B spotted it while styling.
  • 246 words wasn't enough. First playthrough rejected start, spark, ponds. New ticket, 15.9k-word dictionary pulled, reviewed, merged.
  • Stacked PRs → rebase conflicts. Squash-merging the base broke the stack. A human rebase + force-push fixed it; GitHub could not.

A rubber-stamp loop would have shipped all four of these as "working" code.

Why this approach won

What we got

  • Zero merge conflicts across 16 PRs
  • Every teammate ran a review — real bugs caught
  • No one blocked on the others
  • Clean, readable history
  • Shipped the full game in time

Without this?

  • Three people editing one app.js → constant conflicts
  • Claude hallucinations shipping unchecked
  • No shared context → everyone re-explains the goal
  • "It works on my machine" × 3
  • Probably still debugging at the deadline
The bottleneck was never Claude. It was coordination. The methodology solved that, and Claude filled the rest.
